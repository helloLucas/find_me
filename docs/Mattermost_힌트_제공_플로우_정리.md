# 병목 구간 설정 기준

- **클리어 시간 비교**: 각 노드별 표준 클리어 시간을 설정하고, 이를 250% 이상 초과하는 유저 비중이 30%를 넘을 때 병목으로 판단
- **명령어 실패 임계치**: 동일 노드에서 `CH1_FAIL_UNRELATED` 로그가 유저당 평균 7회 이상 발생하면 시스템은 해당 구간을 ‘설명 부족’ 상태로 진단
- **이탈률**: 특정 노드 진입 후 15% 이상의 유저가 세션을 종료하면, 해당 부분이 가장 우선적인 힌트 제공 대상이 됨
- **유휴 및 탐색 오류**: 입력 없이 화면에 머무는 시간이 10분을 초과하거나, 정답과 무관한 이전 페이지를 반복 조회하는 행위 추적

# 전체 파이프라인 흐름

## 1. 실시간 수집: 데이터 적재 (ELK)

- 유저의 모든 행동(클릭, 명령어 입력, 노드 전이)을 JSON 포맷으로 실시간 저장
- `Spring Boot` → `Logstash` → `Elasticsearch` 파이프라인을 통해 유실 없이 중앙 저장소에 쌓음

### 1-1. 로그 생성

유저의 행동이 발생할 때마다 다음과 같은 형태의 행동 로그를 생성하고, 이 로그는 Logback 설정을 통해 `Logstash`로 실시간 전송됨

- 이벤트 발생: 유저가 터미널에 명령어를 입력함
- 데이터 구성:
    
    ```json
    {
      "timestamp": "2026-04-20T10:20:00Z",
      "session_id": "user_7721",
      "node_id": "CH1_TERMINAL_SSH_READY",
      "action_type": "command",
      "input_value": "ssh 172.22.4.19",
      "result": "FAIL_UNRELATED",
      "elapsed_time": 450
    }
    ```
    

### 1-2. Logstash의 정제

Logstash는 들어오는 로그를 Elasticsearch에 넣기 전 가공해야 함

#### [1] Grok 파싱: 비정형 텍스트의 구조화

Spring Boot에서 `log.info()`로 출력된 로그는 원래 한 줄의 긴 문자열임. 이걸 Elasticsearch가 검색하기 좋게 각 항목별로 쪼개는 작업이 필요함

- 원본 로그 예시: `2026-04-20 14:05:01 INFO [user_7721] CH1_TERMINAL_SSH_READY - COMMAND: "ssh 172.22.4.19" RESULT: FAIL_UNRELATED`
- **Grok 필터** 적용: Logstash 설정 파일(`logstash.conf`)에 패턴 정의
    
    ```ruby
    filter {
      grok {
        match => { "message" => "%{TIMESTAMP_ISO8601:timestamp} %{LOGLEVEL:level} \[%{DATA:session_id}\] %{DATA:node_id} - COMMAND: \"%{DATA:input_value}\" RESULT: %{WORD:result}" }
      }
    }
    ```
    
- 결과 (JSON): 원본 로그가 아래와 같이 필드별로 분리됨
    
    ```json
    {
      "timestamp": "2026-04-20 14:05:01",
      "session_id": "user_7721",
      "node_id": "CH1_TERMINAL_SSH_READY",
      "input_value": "ssh 172.22.4.19",
      "result": "FAIL_UNRELATED"
    }
    ```
    

#### [2] 데이터 보정

PostgreSQL 및 Redis와 데이터를 연동할 때 오류가 없도록 정규화하는 과정

- **타임프탬프 통일**: 서버마다 다른 시간 형식을 ISO8601 표준(Elasticsearch 기본 포맷)으로 맞춤
    - 보정 전: `20/Apr/2026:14:05:01 +0900`
    - *보정 후*: `2026-04-20T14:05:01.000Z`
- **데이터 타입 변환**: ‘체류 시간’이나 ‘점수’등은 계산을 위해 숫자로 바꿈
    
    ```ruby
    filter {
      mutate {
        convert => { 
    	    "elapsed_time" => "integer" # 문자열 "450"을 숫자 450으로 변환
    	    "fail_count" => "integer"
    	  }
      }
    }
    ```
    
- IP 정보 보정: `172.22.4.19` 같은 내부 IP가 들어왔을 때, 이를 분석에 용이하도록 정규화하거나 불필요한 공백을 제거함

#### [3] 인덱스 라우팅: 일별 인덱스 관리

Elasticsearch는 데이터가 너무 커지면 검색 속도가 느려짐. 이를 방지하기 위해 Logstash의 Output 단계에서 로그가 생성된 시점을 기준으로 인덱스 이름을 동적으로 지정함

- 동적 인덱싱 설정
    
    ```ruby
    output {
      elasticsearch {
        hosts => ["http://elasticsearch:9200"]
        index => "game-logs-%{+YYYY.MM.dd}"
        template_name => "game-logs-template"
      }
    }
    ```
    
- 작동 예시
    - 4월 20일에 발생한 로그 → `game-logs-2026.04.20` 인덱스에 저장
    - 4월 27일에 발생한 로그 → `game-logs-2026.04.27` 인덱스에 저장

## 2. 주간 분석: 병목 지수 산출

- 매일 새벽, 스케줄러(ex. Celery, Airflow)가 가동되어 하루치 로그 분석
- 위의 [**병목 기준**](https://www.notion.so/3480e0d65bc48033be48cc3bfb23d985?pvs=21)을 적용하여 가장 점수가 높은 노드와 해당 노드에서 가장 빈번했던 오답 명령어 패턴 추출
    - **시간 지수 (30%):** `(해당 노드 유저 평균 체류 시간 / 기획 표준 클리어 시간)`
    - **실패 지수 (40%):** `(FAIL_UNRELATED 결과 카운트 / 해당 노드 진입 고유 세션 수)`
    - **이탈 지수 (30%):** `(해당 노드가 세션의 마지막 로그인지 여부 카운트 / 전체 진입 세션 수)`

### 2-1. 분석 준비

매일 새벽 유저 접속이 적은 시간에 Python 스케줄러 작동

- 작업 내용: `elasticsearch-py` 라이브러리를 통해 어제 인덱스(예: `game-logs-yesterday`)에 접속
- **필터링**: 분석 노이즈를 줄이기 위해 테스트 계정이나 특정 관리자 로그는 제외하고 실제 유저의 `action_type` 로그만 추출

### 2-2. 데이터 집계: 통계 쿼리 실행

Elasticsearch의 집계 기능을 사용하여 서버 단에서 계산된 결과값만 가져옴

#### [1] 노드별 평균 체류 시간 계산

유저가 각 상태(node_id)에서 보낸 시간을 계산함

- **쿼리 방식**: `node_id`별로 그룹화한 뒤, `elapsed_time` 필드의 평균값(`avg`)을 구함
- 앞서 Logstash에서 `mutate`를 통해 `elapsed_time`을 **integer**로 변환했기 때문에 이 단계에서 수학적 평균 계산이 가능함

#### [2] 오답 패턴 및 명령어 실패율 추출

유저들이 어떤 명령어에서 가장 많이 막혔는지 확인

- **쿼리 조건**: `result`가 `FAIL_UNRELATED`인 로그를 대상으로 함
- **핵심 지표**: 특정 노드에서 실패 로그(`FAIL`)의 개수를 전체 액션 수로 나눠 실패율 산출

### 2-3. 병목 지수 계산 로직

추출된 통계치를 바탕으로 Python Worker 내부에서 최종 점수 매김

| **지표** | **계산 공식 (예시)** | **가중치** |
| --- | --- | --- |
| **시간 지수** | (실제 평균 체류 시간 / 노드별 표준 시간) × 100 | 30% |
| **실패 지수** | (특정 노드의 실패 횟수 / 해당 노드 진입 유저 수) × 100 | 40% |
| **이탈 지수** | (해당 노드에서 종료한 세션 수 / 진입 세션 수) × 100 | 30% |

⇒ 최종 점수 = (시간 지수 x 0.3) + (실패 지수 x 0.4) + (이탈 지수 x 0.3)

### 2-4. 최종 결과 도출: 힌트 대상 선정

계산 결과, 가장 높은 점수를 받은 노드를 이번 주의 ‘최악의 병목 구간’으로 선정

예를 들어,

- **대상 노드**: `CH1_TERMINAL_SSH_READY`
- **데이터**: 평균 체류 18분(기준 5분), 실패율 75%, 이탈률 20%
- **최다 오답 텍스트**: `ssh 172.22.4.19` (80% 비중)

## 3. 힌트 생성

- 분석된 오답 데이터를 LLM에 전달하여 가공

### 3-1. 프롬프트 엔지니어링

Python Worker에서 분석한 결과값(`node_id`, 오답 패턴, 통계)을 LLM이 이해할 수 있는 구조화된 지시문으로 만드는 작업.

#### [1] 프롬프트 구성 요소 (예시임)

- **역할 정의**: “너는 게임에서 플레이어의 조력자 역할을 하는 강아지 AI ‘루카스’야. 말투는 귀엽고 친절해야해.
- **분석 데이터**: “지난주 유저들이 `CH1_TERMINAL_SSH_READY` 노드에서 가장 많이 틀렸어. 80%의 유저가 사용자 이름인 `guest@`를 빼먹고 IP만 입력했어.”
- **출력 형식**: "Mattermost에 게시할 것이므로 마크다운 형식을 사용하고, 300자 이내로 작성해줘.”

### 3-2. RAG 결합

PostgreSQL 활용해서 더 정확한 힌트 만들도록 함

- LLM은 정답이 뭔지 모를테니, DB에서 해당 챕터의 정답 가이드(`ssh guest@172.22.4.19`)를 가져와 프롬프트에 포함시킴

#### [1] 스토리 정답 확보

`lucas_knowledge` (pgvector)에서 대상 `node_id`로 `WHERE` 하드 필터링을 걸어 해당 노드의 진짜 정답과 설명을 가져옴

#### [2] 유사 실패 사례 검색

이번 주에 발생한 오답 패턴이 과거에도 있었는지 검색하여 더 누적된 힌트를 제공

- 동작 예시
    - 과거에 생성했던 주간 힌트 문구와 당시의 오답 데이터를 Vector DB(pgvector)에 임베딩하여 저장해 둠 → 이건 지금 없는 것 같긴 함
    - 이번 주 분석 결과가 나오면, 비슷한 유형의 과거 실패 사례가 있는지 벡터 검색으로 찾음
- 활용 예시
    - "이 구간은 한 달 전에도 유저들이 많이 막혔던 곳이야. 그때는 이렇게 해결했었지!"라는 식으로 힌트를 생성할 수 있음
    - 만약 예전 힌트가 효과가 없었다면, LLM에게 "저번 힌트는 반응이 안 좋았으니 이번엔 더 구체적으로 써줘"라고 지시할 수 있음

#### [3] 동적 텍스트 필터링 및 보안 검증

유저의 실제 입력값 중에는 개인정보나 부적절한 언어가 섞여 있을 수 있음. RAG를 이용해 이를 필터링함.

- 동작 예시
    - 유저의 입력 데이터들 중 분석 대상이 되는 텍스트를 임베딩함
    - 금기어 목록이나 게임 세계관 파괴 요소가 담긴 벡터와 대조하여 부적절한 데이터를 걸러냄
- 활용 예시
    - 유저가 입력한 실제 오타 중 가장 적절한 예시만 골라내어 힌트에 활용함으로써 리포트의 질을 높임

#### [4] 유저 수준별 맞춤형 힌트 생성

주간 힌트를 Mattermost에 올릴 때, 하나의 메시지가 아니라 유저 층(초보/숙련자)별로 구분된 멀티 힌트를 생성함

- 동작 예시
    - `pgvector`에 '초보 유저용 가이드'와 '고급 유저용 팁'을 각각 벡터화하여 저장
    - 이번 주 로그 분석 결과, 초보 유저들이 많이 막혔는지 혹은 고인물?들이 특정 최적화 명령어에서 막혔는지 판단
- 활용 예시
    - 메시지: "이번 주에는 뉴비 친구들이 `ssh`에서 많이 헤매더라고!(초보용 힌트) 아, 그리고 만렙 해커 친구들을 위한 `nc` 명령어 꿀팁도 가져왔어!(고급용 팁)"

| **단계** | **기술적 작업 (RAG 활용)** | **데이터 소스** |
| --- | --- | --- |
| **Context Retrieval** | 현재 병목 노드와 가장 유사한 **과거 주간 힌트** 및 **해결 로그** 검색 | **pgvector** (Historical Logs) |
| **Knowledge Injection** | 게임 기획 문서에서 해당 노드의 **상세 로직** 및 **예외 처리 규정** 추출 | **pgvector** (Game Docs) |
| **Persona Tuning** | 루카스의 기존 대화 패턴 벡터를 참조하여 **일관된 말투** 유지 | **pgvector** (Script DB) |
| **Verification** | 생성된 힌트가 실제 정답 가이드와 논리적으로 일치하는지 최종 검증 | **LLM Reasoning** |

## 4. Mattermost 주간 힌트 포스팅

- 생성된 힌트를 Mattermost Webhook을 통해 지정된 사용자 채널에 자동으로 포스팅
- 유저들이 데이터를 시각적으로 이해할 수 있도록 가장 많이 틀린 오답 TOP 3 같은 통계 카드나 이미지를 함께 첨부해도 될 듯
