# EKS/Kubernetes 로그 데이터 분석 보고서

분석 기준일: 2026-05-18  
분석 대상 인덱스: `game-logs-*`  
분석 목적: 최종 발표에서 ELK 기반 로그 수집 결과와 게임/사용자 행동 개선 근거를 설명하기 위한 요약

## 1. 한 장 요약

이번 로그 분석의 핵심은 **16만 건의 raw 로그를 수집했고, 그중 실제 게임 플레이 분석에 사용할 수 있는 구조화 이벤트 9,476건을 분리했다**는 점이다.

| 항목                 |                                            값 | 해석                                            |
| -------------------- | --------------------------------------------: | ----------------------------------------------- |
| 전체 raw 로그        |                                     167,608건 | Filebeat -> Logstash -> Elasticsearch 적재 성공 |
| 구조화된 게임 이벤트 |                                       9,476건 | `result` 필드가 있는 실제 플레이 이벤트         |
| 분석 기간            | 2026-04-30 05:19:29 ~ 2026-05-18 08:09:16 UTC | 구조화 이벤트 기준                              |
| 사용자 수            |                                         159명 | `user_id` 기준                                  |
| 세션 수              |                                         159개 | `session_id` 기준                               |
| 성공 이벤트          |                                6,698건, 70.7% | 정상 진행 이벤트                                |
| 실패 이벤트          |                                2,675건, 28.2% | 사용자가 막힌 지점                              |
| 에러 이벤트          |                                   103건, 1.1% | 시스템/입력 처리 예외 또는 UNKNOWN 전이         |

발표 메시지로는 다음 문장이 가장 좋다.

> 단순히 서버 로그를 모은 것이 아니라, 사용자가 어느 챕터와 어느 노드에서 반복 실패하는지까지 추적할 수 있는 분석 파이프라인을 구성했다.

## 2. 데이터 파이프라인과 분리 기준

로그 수집 구조는 다음과 같다.

```text
Kubernetes container logs
-> Filebeat DaemonSet
-> Logstash
-> Elasticsearch game-logs-*
-> Kibana Discover / Dashboard
```

전체 167,608건 중에는 Kubernetes 인프라 로그와 애플리케이션 일반 로그가 함께 들어 있다. 발표에서는 다음처럼 구분하는 것이 안전하다.

| 구분          | 기준                    |    건수 |   비율 |
| ------------- | ----------------------- | ------: | -----: |
| Raw 로그 전체 | `game-logs-*` 전체 문서 | 167,608 | 100.0% |
| 게임 이벤트   | `result` 필드 존재      |   9,476 |   5.7% |
| 기타 로그     | 인프라/일반 앱 로그     | 158,132 |  94.3% |

구조화 이벤트 9,476건은 모두 `backend` 컨테이너에서 발생했다.

| Namespace |  건수 |  비율 |
| --------- | ----: | ----: |
| `prod`    | 8,889 | 93.8% |
| `dev`     |   587 |  6.2% |

이 구분은 중요하다. “16만 건을 분석했다”라고만 말하면 인프라 로그까지 포함한 값이고, “사용자 행동 분석은 9,476건의 구조화 이벤트를 기준으로 했다”라고 말하면 수치가 훨씬 신뢰 있게 들린다.

- 다음 단계에서는 인프라 로그와 게임 이벤트를 별도 인덱스로 분리하면 Kibana 대시보드 품질이 더 좋아진다.

## 4. 전체 플레이 이벤트 결과

| 결과      |  건수 |  비율 |
| --------- | ----: | ----: |
| `SUCCESS` | 6,698 | 70.7% |
| `FAIL`    | 2,675 | 28.2% |
| `ERROR`   |   103 |  1.1% |

해석:

- 성공률은 70% 수준으로, 대부분의 이벤트는 정상 진행이다.
- 실패가 28.2%로 꽤 높아, 단순 에러 모니터링보다 **사용자 난이도/병목 분석**에 가치가 있다.
- `ERROR`는 1.1%로 낮지만, 일부는 `UNKNOWN` 전이 또는 입력 파싱 오류라서 별도 추적이 필요하다.

발표용 표현:

> 사용자 수는 뒤 챕터로 갈수록 줄어들고, 실패 강도는 week04에서 가장 높게 나타났다. 따라서 개선 우선순위는 week02의 진입 병목과 week04의 고난도 반복 실패 구간이다.

## 8. 실패 입력 패턴

실패가 많은 노드에서 자주 보인 입력 예시는 다음과 같다.

| Node                             | 자주 보인 입력 예시                                                    | 해석                                       |
| -------------------------------- | ---------------------------------------------------------------------- | ------------------------------------------ |
| `CH2_GC_SCAN_ALERT`              | `./laplace_fragment_01.sh`, `laplace_fragment_01.sh`, `cd root`, `tar` | 실행 위치와 파일 실행 방식 혼동            |
| `CH2_LAPLACE_MISSION_READY`      | `sh laplace_fragment_01.sh`, `sh lucas_fragment_01.sh`, `cd root`      | 파일명/경로/실행 순서 혼동                 |
| `CH2_FILE_LIST`                  | `world_map.map`, `cd world_map.map`, `open world_map.map`              | 파일을 읽어야 하는지, 이동해야 하는지 혼동 |
| `CH4_GATE_TRACE_VIEWED`          | `cat /proc/net/tcp/gate_04.trace/...`                                  | trace를 디렉터리처럼 해석하는 경향         |
| `CH4_LAPLACE_ABORTED_DIR_DETAIL` | `mount ...`, `mkdir ...`, `sh lucas_route.sh`                          | mount 대상과 파일 경로를 혼동              |
| `CH1_TERMINAL_SSH_READY`         | `ssh`, `172.22.4.19:22`, `connect_core()`                              | 접속 명령 형식 안내 필요                   |

개선 아이디어:

- 같은 노드에서 `fail_count_after_action >= 3`이면 더 구체적인 피드백을 제공한다.
- `cd root`, `cd root/`, 파일명을 그대로 입력하는 패턴은 초보 사용자가 자주 하는 실수로 보이므로, “파일은 `cat`, 스크립트는 `sh`, 디렉터리는 `cd`” 같은 짧은 맥락 힌트를 추가한다.
- week04는 `ssh`, `mount`, 파일 경로 추론이 동시에 요구되므로, 한 번에 너무 많은 개념이 겹치지 않도록 중간 확인 단계를 둔다.

## 9. 반복 실패와 막힘 정도

`fail_count_after_action` 기준으로 보면 다음과 같다.

| 실패 누적 구간 | 이벤트 수 |  비율 |
| -------------- | --------: | ----: |
| 0              |     6,529 | 68.9% |
| 1-2            |     1,660 | 17.5% |
| 3-4            |       595 |  6.3% |
| 5-9            |       491 |  5.2% |
| 10+            |       201 |  2.1% |

해석:

- 전체 이벤트의 약 31.1%는 이미 한 번 이상 실패한 이후의 행동이다.
- 10회 이상 실패 누적 이벤트가 201건 존재한다.
- 최대 실패 누적값은 34로, 일부 사용자는 특정 지점에서 매우 오래 막혔다.

`fail_count_after_action >= 10` 이벤트의 챕터 분포:

| Chapter  | 이벤트 수 |  비율 |
| -------- | --------: | ----: |
| `week04` |       105 | 52.2% |
| `week02` |        43 | 21.4% |
| `week01` |        35 | 17.4% |
| `week03` |        18 |  9.0% |

즉, 심한 막힘은 주로 `week04`에서 발생한다. 다만 많은 사용자가 처음으로 막히는 지점은 `week02`다.

| `CH1_DARK_ARTICLE_OPEN`      |        5 | 기사 열람 흐름 중 UNKNOWN 발생         |

관측상 `error.message`가 채워진 이벤트는 103건 중 일부에 그친다. 실제로 `error.message.keyword`로 집계된 메시지는 2건뿐이었다.

개선 제안:

- `ERROR` 발생 시 `error.code`, `error.message`, `expected_node`, `actual_input`, `parser_stage`를 반드시 기록한다.
- `to_node_id = UNKNOWN`인 이벤트는 별도 대시보드 패널로 분리한다.
- click 이벤트의 `ERROR`는 사용자 실수라기보다 상태 전이/라우팅 문제일 가능성이 높으므로 운영 버그로 우선 분류한다.

## 12. 발표에 바로 쓸 수 있는 결론

### 결론 1: 수집 파이프라인 검증

ELK 기반으로 Kubernetes 컨테이너 로그를 수집했고, `game-logs-*` 인덱스에 총 167,608건이 적재되었다. 이 중 구조화된 게임 플레이 이벤트 9,476건을 분리하여 사용자 행동 분석에 활용했다.

### 결론 2: 분석 가능한 이벤트 스키마 확보

각 이벤트에는 `user_id`, `session_id`, `chapter_id`, `action_type`, `input_value`, `from_node_id`, `to_node_id`, `result`, `fail_count_after_action` 등이 포함되어 있어, 단순 로그 조회를 넘어 플레이 흐름을 재구성할 수 있다.

### 결론 3: 병목 구간 식별

가장 큰 병목은 `week02`의 `CH2_GC_SCAN_ALERT`, `CH2_LAPLACE_MISSION_READY`와 `week04`의 `CH4_GATE_TRACE_VIEWED`, `CH4_LAPLACE_ABORTED_DIR_DETAIL`이다. 특히 week04는 사용자 수는 적지만 실패율과 실패 누적값이 가장 높다.

### 결론 4: 개선 방향 도출

사용자 실패는 대부분 `command` 입력에서 발생한다. 따라서 UI 클릭 개선보다 명령 입력 피드백, 단계별 힌트, 경로/파일/명령 구분 안내가 우선이다.

## 13. 다음 개선 액션

우선순위 높은 작업:

1. `week02` 진입 병목 완화
   - `CH2_GC_SCAN_ALERT`, `CH2_LAPLACE_MISSION_READY`에서 3회 이상 실패 시 구체 힌트 제공
   - 파일 실행, 경로 이동, 파일 읽기 명령을 구분하는 피드백 추가

2. `week04` 반복 실패 완화
   - `CH4_GATE_TRACE_VIEWED`에서 trace 파일을 어떻게 해석해야 하는지 중간 단계 추가
   - `mount`, `ssh`, 경로 조합 명령에 대해 오답 유형별 피드백 추가

3. 에러 로깅 품질 개선
   - 모든 `ERROR`에 `error.code`와 `error.message` 기록
   - `UNKNOWN` 전이를 별도 오류 타입으로 분리

4. 인덱스/대시보드 정리
   - 게임 이벤트: `game-events-*`
   - 인프라 로그: `infra-logs-*`
   - Kibana Dashboard: 일별 이벤트 수, 챕터별 성공률, 실패 상위 노드, 고반복 실패 세션, ERROR 전이
